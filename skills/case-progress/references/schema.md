# case.yaml v4.0 字段字典（唯一权威契约）

> **版本**: 4.0（2026-08-14 定稿）
> **权威声明**：本文件是 case.yaml 的唯一字段契约。new-case 模板生成、case_store 引擎校验、M4 存量迁移、case-dashboard 渲染，一律以本文为准；其他 skill 引用版本号，不复制内容。
> **上位设计**：消费项目 SuitAgent《case-dashboard 与数据真值统一方案》v1.6（§3 数据真值规范，决策 #045/#046）。

---

## 0. 设计原则

1. **状态与叙事分离**：case.yaml 只存可计算状态；案情细节在 `<案件ID>案件信息.md`（叙事文档），经 `上下文.叙事文档` 指针关联。
2. **字段准入**：每个字段必须标注消费者（dashboard / agent / lawyer / new-case / case_store），无消费者不收录。
3. **人工覆盖保护**：行级 `source: user|ai`；AI 永不覆写 source=user 的行；`生命周期状态=已结案` 仅手工标记；`程序阶段锁定=true` 时 AI 不得改写程序阶段。
4. **数据卫生**：
   - 日期一律 `YYYY-MM-DD`（模糊年份允许 `YYYY-MM`）；禁止 `2025年10月`、`待定` 等混排
   - 占位符统一 `null`，说明写进对应 `备注` 字段；禁止 `[待确认]`、`__________`、空串冒充
   - 枚举值纯净不带 emoji（⭐/✅ 等由展示层添加）
   - 金额为数值（默认 CNY），不带单位、不带千分位
   - 禁止绝对路径；所有路径相对 case.yaml 所在目录
5. **行键（稳定身份）**：列表行的身份用业务键，不用数组下标——AI 重排后人工修改不错位。

| 列表 | 行键 |
| --- | --- |
| 任务 | 存储字段 `id`（task_001 递增，创建后不变） |
| 法定期限 | `类型\|名称` 复合键（不存储，派生） |
| 案件时间线 | `日期\|事件类型` 复合键 |
| 当事人（我方/对方） | `姓名\|角色` 复合键 |
| 证据索引 | `名称` |
| 索赔与评估 | `项目` |
| 更新历史 | 追加式，无行键 |

**状态三态**（全库统一，替代各格式旧值）：`todo` / `in_progress` / `done`。

### 2.8 费用信息（二域：支出成本 + 索赔评估）

**支出**（map）：`律师费 / 诉讼费 / 鉴定费 / 其他费用`，每项 `{金额: number|null, 状态: 已确定|待确定}`；律师费另含 `计费方式: 固定|风险|阶段`（风险代理、分阶段收费为真实形态）——终结对象/扁平串/markdown 表三种结构并存。

### 2.14 审级记录（litigation，行键 = 审级）

一案跨多审级时每审级一行（借鉴 CaseBoard case_instances 的简化）：`{审级: enum✅（一审|二审|再审|执行|仲裁）, 法院案号: str|null, 承办法官: str|null, 法院联系方式: str|null, 立案日期: date|null, 结案日期: date|null, 结案方式: str|null（判决|调解|撤诉|裁定）, source}`。meta.法院案号 为**当前审级案号**的快捷方式，二者不一致时以本表为准；法官/助理/书记员、法院电话（判决书与传票中的真实信息）落此表。

### 2.15 开庭与听证（litigation，行键 = 日期|类型|次序）

`{日期: date✅, 类型: enum✅（开庭|听证|谈话|质证）, 地点: str|null, 法庭: str|null, 事项: str✅, 次序: int|null（第几次）, 来源文件: str|null, 状态: enum✅（todo=已排期未开|done=已进行）, source}`——材料盘点确认：多轮庭审跨月进行、听证传票含完整时间/地点/法庭号为真实形态；M5 月历视图的直接数据源。时间线仍记一条对应事件（事件类型=开庭），明细在本表。

### 2.16 扩展信息（core，类型档案插件容器）

```yaml
扩展信息: {}        # 非诉/领域插件的命名空间，如：{商标: {申请号: ..., 类别: [...], 续展截止: ...}, 专利: {...}}
```

规则见 §7：容器机制现在定型，具体字段**惰性定义**（某类非诉项目实际接入时才立档案，遵循字段准入原则）。litigation 案件此节保持空 map 或省略。

### 2.17 更新历史（追加式）

`{日期: date, 操作者: str（case_store/律师名/agent 名）, 动作: str, 细节: str}`——统一五种旧字段集（action/更新原因/备注/版本 语义并入 动作/细节）。

## 4. 存量格式 → v4.0 映射要点（M4 迁移依据）

| 来源 | 关键映射 |
| --- | --- |
| A（v2.1.0 英文） | case_name→案件名称；case_status→生命周期状态；current_stage→程序阶段；tasks[]→任务（id 直接沿用）；legal_deadlines→法定期限（补类型归类）；important_dates→案件时间线（category→事件类型尽力映射）；双 yaml 案件（A 类特有）先合并再映射 |
| B（v3.0 中文） | 按 §3 处置表直迁；时间线节点 执行状态→任务/时间线状态（优先映射已有状态） |

## 5. 校验规则（case_store validate 依据）

1. 必填字段齐全且类型正确；枚举值在 §2 定义范围内
2. 所有日期匹配 `^\d{4}-\d{2}(-\d{2})?$`；金额为数值
3. 每个列表行含合法 source；任务 id 全局唯一
4. `程序阶段锁定=true` 时记录最后修改者为 user
5. 无绝对路径（`^/` 或盘符开头即报错）
6. 生命周期状态=已结案 的案件：提示确认（只应经手工操作产生）

## 7. 类型档案（Profile）与非诉扩展机制

**问题**：律师业务不止诉讼（new-case 已有 商标/专利/咨询 预设），但各领域字段差异大（商标要申请号/类别/续展，专利要年费/审查阶段），诉讼核心字段（审级/开庭/争议焦点）对非诉无意义。

**机制**（三层，借鉴 CaseBoard 的 case_type 二分 + 我们的字段准入原则）：

1. **core 层**（§1 表标注 core/对抗性的节）：一切案件必填——meta（含 业务领域 路由键）、案件基本信息（生命周期状态通用；程序阶段按档案取枚举）、当事人与代理（我方=客户方）、任务、时间线、费用、上下文、扩展信息、同步、更新历史。
2. **类型档案**：每个非诉领域的专属字段定义为其档案，落 `case-progress/references/profiles/<领域>.md`（如 `trademark.md`），内容 = 该领域的 扩展信息.命名空间 字段表 + 程序阶段枚举 + 额外节定义；**惰性立项**——某领域第一个真实项目接入 case.yaml 时才创建档案，字段必须逐一过字段准入原则（有消费者才收录），不做投机设计。
3. **配套演进**：new-case 对应预设升级为生成 core + `扩展信息.<领域>` 骨架；case_store 的 validate 按业务领域加载对应档案校验；dashboard 对未知领域节做通用渲染（key-value 表格降级）。

**接入流程**（以商标为例）：新建商标项目（new-case trademark 预设）→ 发现无 trademark 档案 → 按该项目真实材料起草 profiles/trademark.md（走本 schema 的评审）→ new-case 模板补骨架 → 完成。存量诉讼案件不受影响（业务领域=诉讼，litigation 节生效）。
