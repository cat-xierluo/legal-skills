# Agent 产物的保留与调整

路径只能提供线索；先量大项，再识别用途。读取内容不是默认步骤，需要确认重建入口时只读必要的清单、构建参数和引用，避开客户材料和会话正文。

| 类型与常见位置 | 默认判断 | 建议调整前需要的证据 |
| --- | --- | --- |
| 模型权重：Hugging Face、Ollama、LM Studio 等实际模型目录 | 可重复下载，但可能支撑本地 ASR/TTS/离线任务 | 模型名称、版本、唯一权重、消费者、下载成本及是否在用；由所属模型管理器处理，不按后缀删 |
| 包管理器缓存：npm `_cacache` / `_npx`、uv/pip 下载缓存 | 通常可再生，适合作为优先核查项 | 区分缓存与已安装运行环境；使用对应管理器支持的命令，不碰正在安装的事务 |
| Agent 日志、会话、任务、数据库、file-history | 工作记忆和恢复材料，不能整体视为缓存 | 生命周期、恢复需要、保留策略；数据库 WAL/SHM 不能单独删，不能按 JSONL 扩展名整批清 |
| Agent 配置目录中的 `.git` | 是历史对象库，不是普通缓存 | 区分工作区当前文件、历史大对象和未推送成果；交 Git 专项审计，不直接删对象库 |
| worktrees / Orca 工作区 / 临时目录内的 Git 树 | 分支成果、未跟踪素材和任务现场 | common-dir、完整 HEAD、dirty/index、ignored/untracked、owner、原任务、实际占用与可恢复性；进程/cwd 无命中不证明无人使用 |
| 构建产物：`target` / `dist` / `build` / `node_modules` / `.venv` | 可能可重建，也可能是实际运行/安装入口 | 锁文件与版本、离线需求、安装链接和运行中消费者；先避免多树重复构建，不能只凭目录名删 |
| 可视化：HTML/SVG/JS、Blender/CAD、视频工程、配音与图片 | 源文件和独有素材通常必须保留 | 最终交付件、可编辑工程、外链/本地引用、字体/素材/音频、重建命令与参数是否齐全 |
| 可视化中间文件：逐帧 PNG、临时 WAV、代理视频、多轮编码 | 确认可重建后才是候选 | 消费引用和重建链；先保留成品+工程+独有输入+少量代表性验证证据，再讨论中间帧 |
| 截图/录屏、法律材料、测试金样 | 可能是唯一证据或回归基准 | 来源、验收/诉讼用途、是否另有原件；不按年龄或尺寸统一清理 |

## 可视化目录中的混合用途

`~/.codex/visualizations` 等目录可能同时放正式成品、源材料、开发工作树、依赖和运行报告。应分别回答：

- 真正的图像/视频成品有多大？哪些正在展示、分享或被文档引用？
- 占用是否主要来自嵌套的工作树、`node_modules`、`target`、`.venv`、帧缓存？
- 同一内容多轮版本是否含人工修订、独有声音或素材？仅元数据相似不能证明重复。
- 是否能用“小型成品预览 + 项目源文件 + 必需素材 + 重建说明”保留成果？用户选定归档位置后再迁移并核引用，不能先移动造成断链。

“压缩一下”也可能引入新副本和峰值空间；磁盘紧张时先算新增临时空间。APFS 克隆、硬链接和快照会影响释放量，删除后的 `df` 变化才是实际收益证据。

## 防止再次膨胀

按本次最大来源给针对性建议，不一律套用：新 Skill 工作树创建时稀疏；复用与串行构建减少依赖副本；中间帧按已验收任务收尾；模型按消费者而非每项目下载；临时产物与长期成果各有明确位置和保留条件。不要建立自动按天删除 `visualizations` 的计划。若用户要周期监测，另行创建有范围的只读监测，仅在明显变化时通知。
