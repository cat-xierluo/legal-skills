## 0. 起源与动机（保留 brainstorming 完整背景）

> 这一节是后人理解"为什么要做这个 skill"的关键。完整 brainstorm 上下文同时沉淀在 `../DECISIONS.md` 顶部"起源与动机"section。

### 用户原始痛点（2026-08-12 brainstorming 起手）

杨卫薪律师观察到：

> "很多人用 AI ，一开始用不好，可能就要从最基础。的这个关于 harness 的初始化配置去讲起。比如项目的 agentsmd 要怎么配？用户的 agentsmd 要怎么配？他要根据自己所做的工作工作不同内容去做调整的，因为这个说是实际上是发给 agent 的 session 的最重要的一句话了。"

提炼为三个核心：

1. **多数法律人 AI 协作失败的根本原因**：harness（AGENTS.md / CLAUDE.md）没配对
2. **AGENTS.md 的真正重要性**：是发给 agent session 的**最重要的一句话**——比单次 prompt 更重要，因为它决定所有后续会话的默认行为
3. **分层视角**：用户级 vs 项目级，且要根据工作内容调整

### 命名决定

`Legal Harness Init`——明示"法律人 + harness 初始化"，区别于现有的 `project-init`（项目脚手架）。

### 与 `project-init` 的边界（用户主动澄清）

`project-init` 做 **skill 配置**（项目脚手架、docs 体系、settings.json）；

本 skill 做 **agent 层配置**（AGENTS.md / CLAUDE.md 的生成与写入）；

做成 skill 的工具属性：导入即写入当前 session——这是与"通用文档生成"的本质区别。

### brainstorming 阶段 5 个关键转折

| 转折 | 洞察 | 设计影响 |
|---|---|---|
| **用户级 vs 项目级差异** | 用户原话："用户级别的 AGCM 配置应该差不多的，差异比较大的是项目级别的" | 用户级短流程（5-10 问）+ 模板化；项目级长流程（8-15 问）+ 引导式 |
| **回溯契约的引入** | 用户原话："我们法律人在做工作的时候，可能需要的就是 AI 它做一些关键工作的时候，你要有回溯，也就是写入到类似这个 Change log decisions 以及 task gem 地址之类的文件当中"（CHANGELOG/DECISIONS/TASKS） | 法律人 AGENTS.md 必须内置"AI 必须留痕"的契约——这是与普通 AGENTS.md 的最大差异 |
| **模块化 vs 预设的反思** | 用户原话："我不太确定这里面的这个预设够不够...我们只写到底要保、要要有哪些模块就行了呢？" | 8 模块为骨架（M1-M8），5 预设降级为 references/17-examples/ 参考范例 |
| **形态双层** | "从基础讲起 + 导入即写入"对应教学底座 + 生成入口 | references/ 教学底座 + SKILL.md 主流程；agent 必须主动引用教学章节 |
| **Harness 覆盖** | 用户原话："在哪个平台使用就写入哪个平台" | 检测 4 平台（CC/Codex/OpenClaw/QoderWork），按检测到的写入 |

### 不做什么（避免范围蔓延）

- 不重复 `project-init`（项目脚手架）
- 不做跨行业通用（法律专供）
- 不主动重写用户已有 AGENTS.md（必须 diff 让用户决定）
- 不做 skill 内容开发、代码生成、OCR 等业务侧工作

## 1. 目标与非目标

### 1.1 一句话目标

让法律人能用最少的专业成本，把"AGENTS.md / CLAUDE.md 是发给 agent session 的最重要的一句话"这件事写对——既有人人能懂的原理讲解（教学底座），又能直接帮他生成并写入当前环境（生成入口）。

### 1.2 目标

- 让"一开始用不好 AI"的法律人理解**为什么** AGENTS.md 重要、用户级 vs 项目级怎么分、为什么要写"回溯契约"。
- 帮法律人快速生成**用户级** AGENTS.md（个人工作偏好、角色身份、回溯契约总开关）。
- 帮法律人在新接的**案件/项目**里补齐**项目级** AGENTS.md（回溯契约条款 + 法律工作流约束 + 项目特定上下文），不与 `project-init` 重复。
- 默认覆盖法律人最常用的项目类型：诉讼 / 非诉合同 / 知产 / 企业法务 / 法律研究（采用**模块化为骨架 + 预设降级为参考范例**方案，见 §6）。

### 1.3 非目标

- **不**重复 `project-init` 的通用项目脚手架（skills 安装、settings.json、docs 体系、.codex、.gitignore）。两者互补不互替。
- **不**做跨行业通用 harness 配置。法律专供，命名 `legal-harness-init` 名实相符。
- **不**做 skill 内容开发、代码生成、OCR 等业务侧工作。
- **不**主动重写用户已有的 AGENTS.md/CLAUDE.md。已有时展示 diff，由用户决定合并/跳过。

## 2. 受众与场景

| 受众 | 典型场景 | 痛点 |
|---|---|---|
| 第一次用 AI 协作的律师 | "听说 AI 能帮我审合同，但每次都要从头讲一遍我是律师" | 不知道怎么写、写在哪、和每次对话什么关系 |
| 有一定 AI 使用经验但配置混乱的律师 | 已经有过几次会话，但每次都要重新交代角色和工作流 | 用户级没写、项目级没沉淀，工作偏好散落在 prompt 里 |
| 律所技术对接人 / 团队 lead | 想给团队成员配一套统一基线 | 没现成模板、不知道不同业务方向配置差异 |

## 3. 核心定位

**教学底座 + 生成入口**，两层互补：

- **教学底座**（references/）：系统讲清 AGENTS.md 的原理、用户级/项目级分工、各模块设计原理、回溯契约怎么写、按法律工作流怎么落地。**这份底座本身就是 skill 的活教材**。
- **生成入口**（SKILL.md 主流程）：按"先用户级、后项目级"顺序引导用户产出真实的 AGENTS.md 文件，落到对应平台的对应位置。

## 4. 形态与双层入口

### 4.1 双层入口策略

**先用户级，后项目级**。理由：
- 用户级差异小、模板化强（一份预设 + 是否开回溯契约 + 个人偏好），可短流程快速出活。
- 项目级差异巨大（案件类型、委托人、阶段、文件结构、对外回溯要求），是教学底座和问答的主战场。
- 教学节奏贴合"先想清楚我是谁、再想这个项目是什么"。

### 4.2 用户级流程（同质化高 → 短流程）

按 8 模块顺序走（M1 → M2 → M3 → M4 → M5），每个模块 1-3 个引导问答。

```
M1 角色身份：你的角色？主要业务方向？执业地域？
M2 工作流与产出：你最常做的几类工作？产出什么文档？
M3 协作偏好：详尽还是简洁？批注还是修订？中英文？
M4 工具链与禁区：允许/禁止的工具？必须人工复核的动作？红线？
M5 回溯契约：是否开启（默认开）→ 勾选通用触发场景
→ 直接生成并写入（按检测到的平台写所有位置的 AGENTS.md）
```

预计 **5-10 个问答**，由 M1-M5 拼接出用户级 AGENTS.md。预设不直接套用，但 agent 在用户卡壳时可调出 references/17-examples/ 对应范例作为参考。

### 4.3 项目级流程（差异大 → 引导式长流程）

按 M6 → M7（动态） → M8 → M5（项目级细化） 顺序走。

```
1. 检测项目目录：是否已有 AGENTS.md？是否已经跑过 project-init？
2. M6 项目上下文：什么类型（诉讼/非诉/知产/法务/研究）？编号？委托人？当前阶段？
3. M7 案件/项目关键事实：按所选项目类型动态问（见 §6.2 表）
4. M8 文件结构约定：用什么目录模板？命名约定？哪些文件不进版本？
5. M5 项目级细化：本项目有没有特殊的回溯要求（叠加用户级总开关）？
6. 与 project-init 协作：检测到已跑过则只补"法律人设 + 回溯契约 + 法律工作流约束"三块；未跑过则提示用户"建议先跑 project-init 再用本 skill 补法律专属"
7. 写入并展示 diff
```

预计 **8-15 个问答**，由 M6-M8 + M5 细化拼接出项目级 AGENTS.md。agent 在用户卡壳时可调出 references/17-examples/ 对应类型范例作参考。

## 5. Harness 覆盖：检测所有已装平台，按平台写入

**原则：在哪个平台使用就写入哪个平台**——agent 启动时检测当前环境安装了哪些 harness，对每个检测到的平台都生成/同步写入。

| 平台 | 用户级位置 | 项目级位置 | 备注 |
|---|---|---|---|
| Claude Code | `~/.claude/CLAUDE.md` | `<project>/CLAUDE.md`（@include AGENTS.md） | 主战场 |
| Codex | `~/.codex/AGENTS.md` | `<project>/AGENTS.md` | 主战场 |
| OpenClaw | `~/.openclaw/AGENTS.md`（或等价） | `<project>/AGENTS.md` | 按平台格式调整 |
| QoderWork | `~/.qoderworkcn/AGENTS.md`（或等价） | `<project>/AGENTS.md` | 按平台格式调整 |

**同步机制**：
- 用户级：CC 和 Codex 的用户级文件**分别维护**（不要用 @include，因为不在同一目录）。本 skill 给每个平台各自生成一份等价但适配格式的内容。
- 项目级：项目内一份 `AGENTS.md` 作为真值源，CC 的 `CLAUDE.md` 和其他平台的入口都 `@include ./AGENTS.md`，单一维护。

**检测逻辑**：复用 skill-manager 的检测机制（已有 4 平台支持），扫描用户目录和项目目录哪些平台有配置痕迹（`.claude/` / `.codex/` / `.openclaw/` / `.qoderworkcn/`）。

## 6. 模块化方案：8 模块为骨架，预设降级为参考范例

> **设计哲学**：法律工作多样性远超预设能覆盖的范围。与其给用户 5 套"标准答案"，不如教他们"AGENTS.md 应该包含哪些维度"，让他们和 agent 一起拼装出真正贴合自己的配置。
>
> 5 套完整范例（诉讼 / 非诉合同 / 知产 / 法务 / 研究）保留为"参考范例"放在 `references/17-examples/`，作为"完整长什么样"的展示，**不是可套用的预设模板**。

### 6.1 8 个核心模块

agent 按模块顺序引导用户，每个模块对应 AGENTS.md 的一段内容。

| # | 模块 | 答什么 | 用户级/项目级 | 关键问题 |
|---|---|---|---|---|
| M1 | **角色身份** | 我是谁 / 做什么法律工作 / 执业地域 | 用户级 | 你的角色（律师/法务/学者/培训师/复合）？主要业务方向？执业地域？ |
| M2 | **工作流与产出** | 常用文档/动作清单 | 用户级 | 你最常做的几类工作？产出什么类型的文档？ |
| M3 | **协作偏好** | 详略/术语/批注风格/语言 | 用户级 | 你希望 AI 怎么和你协作？详尽还是简洁？批注 vs 修订？中英文？ |
| M4 | **工具链与禁区** | 允许/禁止的工具/动作/红线 | 用户级 | AI 可以用什么工具？绝对不能做什么？什么必须人工复核？ |
| M5 | **回溯契约** ⭐ | 哪些动作必须留痕 + 写到哪些文件 + 格式 | 用户级（基础）+ 项目级（细化） | 哪些动作必须留痕？写到哪里（DECISIONS/CHANGELOG/TASKS）？ |
| M6 | **项目上下文** | 项目类型/编号/委托人/阶段 | 项目级 | 这是什么类型的法律工作（诉讼/非诉/知产/法务/研究）？编号？委托人？当前阶段？ |
| M7 | **案件/项目关键事实** | 案号/对手/管辖/关键时点（诉讼）；申请号/类型/节点（知产）……按项目类型动态问 | 项目级 | 按所选类型动态问（见 §6.2） |
| M8 | **文件结构约定** | 是否用 new-case 模板 / 目录命名 / gitignore | 项目级 | 用什么目录模板？命名约定？哪些文件不进版本？ |

### 6.2 M7 按项目类型动态问

| 项目类型 | 必问 | 可选问 |
|---|---|---|
| 诉讼 | 案号、管辖法院、对方当事人、当前阶段、开庭日期/举证期限 | 律师团队、案件标的、是否涉外 |
| 非诉合同 | 项目编号、业务类型（DD/谈判/签约/交割）、客户、对方主体 | 标的项目金额、是否跨境 |
| 知产 | 申请号、类型（商标/专利/著作权/商业秘密）、商品/分类号、当前阶段 | 驳回/复审状态、续展/年费节点 |
| 企业法务 | 服务对象（部门/业务线）、服务范围、当前重点 | 集团架构、合规体系 |
| 研究 | 课题、委托方、截止日期、预期交付物 | 研究范围限定、引用格式要求 |

### 6.3 M5 回溯契约（最关键模块）

详见 §11。生成入口在用户级首次回答 M5 时给出基础版本（默认开启 + 通用触发场景），项目级流程结尾再问一次"本项目有没有特殊的回溯要求"以细化。

### 6.4 模块拼装规则

按模块顺序收集答案 → 每个模块取"用户回答 + 最贴近的片段库片段" → 按固定模板拼装成最终 AGENTS.md：

```
# {M1 角色摘要}

## 工作流与产出
{M2 内容}

## 协作偏好
{M3 内容}

## 工具链与禁区
{M4 内容}

## 回溯契约
{M5 内容}

---

# 项目：{M6 项目类型 + 编号}

## 上下文
{M6 内容}

## 关键事实
{M7 内容}

## 文件结构
{M8 内容}

## 项目级回溯补充
{M5 项目级细化内容}
```

### 6.5 5 套参考范例的位置和用途

放在 `references/17-examples/`：
- `full-example-litigation.md`
- `full-example-transactional.md`
- `full-example-ip.md`
- `full-example-in-house.md`
- `full-example-research.md`

**用途**：
1. 用户在某个模块不知道怎么答时，agent 主动调出"诉讼律师通常在 M5 写这些……"做参考。
2. 教学底座中"好 vs 坏"的完整对照样本。
3. 新人学习的"完整长什么样"展示。

**非用途**：不直接套用，不强制要求用户按范例写。

## 8. 生成入口交互流程（SKILL.md 主流程）

### Step 1: 启动与问候

简要说明本 skill 做什么、问用户"先做用户级还是项目级"（默认按"先用户级后项目级"）。

### Step 2: 检测环境

调 `scripts/detect.sh` 返回：
- 检测到哪些 harness（CC / Codex / OpenClaw / QoderWork）
- 各平台用户级文件是否存在、内容长度
- 当前 cwd 是否有 AGENTS.md / CLAUDE.md
- 当前 cwd 是否已经跑过 project-init（探测 `.claude/skills/`、`docs/` 是否存在）

### Step 3: 选层级

按用户选择进入用户级或项目级流程。

### Step 4: 用户级流程（如选）

按 §4.2 5-10 个问答，引用 references/ 相关章节穿插讲解。最后生成内容，先展示 diff/预览让用户确认，再按检测到的平台逐个写入。

### Step 5: 项目级流程（如选）

按 §4.3 8-15 个问答，**问题按所选项目类型动态调整**（诉讼问案号，知产问申请号）。引用 references/07-14 相关章节。生成时按互补原则：
- 已跑过 project-init → 只补"法律人设 + 回溯契约 + 法律工作流约束"三块，append/merge 到现有 AGENTS.md。
- 未跑过 → 提示用户"建议先跑 project-init"，但仍可先生成"法律人设 + 回溯契约"的核心三块（项目级其余部分后续由 project-init 补齐）。

展示 diff 让用户确认后写入。

### Step 6: 报告与下一步建议

- 已写入的文件清单（按平台）
- 下一步建议（用户级完成后可做项目级 / 已跑过 project-init 提示补项目级法律块 / 等）

## 10. 写入实现：SKILL.md 指引 + 最小入口脚本

**SKILL.md 负责**：所有对话、问答、决策、生成、合并、写入都由 agent 按 SKILL.md 步骤执行。

**scripts/detect.sh 负责**：一次性检测，返回结构化信息，让 agent 决定后续怎么走。检测项：
- 各 harness 用户级配置是否存在
- 项目级 AGENTS.md/CLAUDE.md 是否存在
- project-init 是否已跑过（.claude/skills/、docs/ 存在性）
- 报告各文件大致行数（决定是否要展示完整 diff 还是摘要）

**为什么不写完整脚本**：
- 保持 skill 轻量、易维护
- 教学底座的"活教材"理念要求 agent 必须深度理解每一步
- 完整脚本容易陷入 project-init 那种"硬编码预设不灵活"的状态

## 11. 法律人专属：回溯契约机制（核心 section）

这是本 skill 与普通 AGENTS.md 配置的**最大差异**，必须作为 references/05 的核心内容独立成节。

### 11.1 触发场景（按项目类型定）

每个项目类型都定义自己的回溯触发清单（与 §6.2 项目类型表对齐）：

| 项目类型 | 必须回溯的动作 |
|---|---|
| 诉讼 | 案号/管辖/对方变更、新增证据材料、策略调整、对外发送文书 |
| 非诉合同 | 合同版本切换、关键条款决策（管辖/责任/担保/价款）、里程碑事件（签约/交割） |
| 知产 | 申请号/阶段变更、驳回/复审/无效决策、续展/年费节点 |
| 企业法务 | 合规审查结论、模板修订、风险事件 |
| 法律研究 | 研究思路与取舍、检索结果、案例汇编节点 |

### 11.2 写入文件契约

| 动作 | 写到哪里 | 字段 |
|---|---|---|
| 重要变更/决策 | `docs/DECISIONS.md` | 决策标题、日期、背景、选项、决定、影响 |
| 可观测的历史变更 | `CHANGELOG.md` | 版本、日期、变更类型、影响范围 |
| 待办/进行中事项 | `TASKS.md` 或 `status/TASKS.md` | 任务、状态、负责人（如有）、截止 |

### 11.3 写入原则（写入 AGENTS.md 的措辞范本）

```
## 回溯契约（Audit Trail Contract）

我是法律工作者，AI 在协助我工作时，必须把以下"关键动作"按以下规则留痕：

### 必须回溯的动作
（按当前项目类型自动填入，见 §11.1 表）

### 回溯位置
- 重要决策 → docs/DECISIONS.md
- 用户可见变更 → CHANGELOG.md
- 进行中/待办 → TASKS.md（或 status/TASKS.md，按项目约定）

### 回溯原则
- 每次写入必须含日期（YYYY-MM-DD）、上下文、动作、影响
- 不替我下"实质性结论"，但要把达成结论的过程完整留痕
- 不删除已有记录，只追加或标记作废
- 写入前先检查目标文件是否存在、是否已记录同类内容，避免重复
```

## 12. 与 project-init 的互补边界

| 职责 | project-init | legal-harness-init |
|---|---|---|
| 用户级 AGENTS.md | ❌ 不做 | ✅ 做（法律人设 + 回溯契约 + 工作偏好） |
| 项目级 AGENTS.md | ✅ 做（生成项目协议 + docs 体系） | ✅ 做（叠加法律人设 + 回溯契约 + 法律工作流约束） |
| 项目脚手架（.claude/.codex/settings/skills/docs/.gitignore） | ✅ 做 | ❌ 不做 |
| 检测项目类型 | ✅ | ❌（按用户告知/手动选预设） |
| 安装 skills | ✅ | ❌ |
| 生成 docs/ 体系 | ✅ | ❌ |
| 生成 settings.json / .gitignore | ✅ | ❌ |

**协作点**：legal-harness-init 的 detect.sh 检测到项目已跑过 project-init 时，只补"法律人设 + 回溯契约 + 法律工作流约束"三块到现有 AGENTS.md，不重写其他部分。

## 13. 错误处理与边界

- **检测不到任何 harness** → 提示用户"当前环境似乎没安装 Claude Code / Codex 等，本 skill 需要至少一个 harness 才能写入"，并退出。
- **用户级文件已存在且非空** → 展示 diff 让用户决定覆盖/合并/追加，默认不覆盖。
- **项目级 AGENTS.md 已存在但不含回溯契约** → 提示"已检测到现有 AGENTS.md，建议只追加法律人专属三块"，默认 append，不重写。
- **项目级 AGENTS.md 已存在且含法律人设** → 提示"已检测到法律人设，是否需要更新模块配置/回溯契约配置项"，进入更新模式而非首次写入。
- **用户中途放弃** → 不写任何文件，保留已完成问答供下次接续。
- **跨平台同步冲突** → 用户级各平台独立写，写入前展示差异（CC vs Codex 文件差异），由用户确认。
