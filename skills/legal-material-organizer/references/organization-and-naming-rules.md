# 文件整理与命名规则

## 核心边界

本 skill 的目标是让新材料"先入库、看得懂、找得到、交得出去"，不是完成案件分析。

允许做：

- 文件分类
- 内容识别
- 文件命名
- 文件夹重组（带序号）
- 整理后回更新引用
- 待人工确认清单
- 参照度评估

不做：

- 案件事实提取
- 争议焦点判断
- 证明目的分析
- 诉讼策略或法律意见

## 编号体系：入库身份与展示编号分离

### 后台入库身份

`material_id` 是 archive JSON 中的稳定主键，格式为 `M-000001`。它只用于增量扫描、来源链、处理记录和旧 manifest 迁移，不出现在律师阅读的 Markdown 报告和整理后文件名中。

### 前台展示编号

`display_code` 是律师可见编号，格式为 `{参照度}{三位序号} {描述}.{扩展名}`，例如 `A001 初次咨询录音转写.md`。展示编号由整理计划生成，可以随内容理解和案件上下文分析更新。

### 参照度级别

| 级别 | 含义 | 适用材料 |
|------|------|----------|
| A | 当前工作材料，优先阅读 | 一手沟通、当前确认清单、持续更新的工作记录 |
| B | 常查，反复引用 | 录音转写、核心截图、订单数据、合同原件 |
| C | 存档，低频查阅 | 辅助说明、重复截图、低信息量材料 |
| D | 待激活，转化时可能需要 | 压缩包原件、未处理原始文件 |

### 评估规则

在完成内容理解（Step 3-4）后，根据以下规则判定参照度：

| 材料特征 | 参照度 | 判定依据 |
|----------|--------|----------|
| 律师-客户沟通记录（咨询录音转写、面谈纪要） | A | 一手信息源，阅读优先级高 |
| 当前确认清单或持续更新的工作记录 | A | 需要反复维护和查阅 |
| 录音转写（信息密度高） | B | 需要反复引用关键表述 |
| 关键聊天截图 | B | 需要反复查阅可见内容 |
| 订单数据、交易记录 | B | 数据型材料，需要反复查对 |
| 合同原件 | B | 核心法律文件 |
| 辅助说明或历史问答 | C | 低频查阅 |
| 重复截图（内容基本相同） | C | 信息冗余 |
| 压缩包原件 | D | 已拆包处理，原始件保留备查 |
| 未处理原始文件 | D | 待后续处理 |

### 展示编号规则

- **序号全局唯一不重叠**：A001、A002、B003、C004...
- **A 级内部排序原则**：一手沟通记录 → 当前确认清单 → 持续更新的工作记录
- **初始状态**：扫描时统一设为 `reference_level = D`、`reference_score = 0`，展示为 `D001`、`D002`
- **参照度可调整**：随项目进展可升降级，调整时更新 `display_code`、文件名和材料清单，但不修改 `material_id`

## 命名原则

文件名应回答四个问题：

1. 这是什么材料（展示编号）
2. 大概涉及什么内容
3. 如能确认，是什么时间
4. 对应哪个展示编号（容器来源）

推荐格式：

```text
{display_code} {内容关键词} - {补充说明}.{原扩展名}
```

示例：

```text
A001 律师-客户初次咨询录音转写-5月19日.md
A002 当前材料确认清单.md
A005 补充材料跟进记录.md
B012 聊天截图-交付时间确认-1.jpg
B018 转账记录 - 付款凭证.jpg
C019 历史问答记录.docx
D008 沟通记录导出包.zip
```

## 文件夹命名规则

### 既有案件结构优先

整理前先读取目标案件根目录的一级目录、材料清单、项目信息和管理文件，推断现行结构。分类目标按以下优先级确定：

1. 用户本次明确指定的目录。
2. 当前案件目录中已经稳定使用的分类、编号和命名规则。
3. 与 new-case 预设或个人本地规范兼容的缺省规则。
4. 前述均无法确定时，向用户确认或归入待确认目录。

不得检测到某种预设后重建案件目录。只有现有结构没有合适类别、且用户确认后，才创建最小新增目录。new-case 仅提供可识别的结构来源，运行时不需要调用或交接。

### 无案件结构时的通用规则

文件夹按材料类型或主题分组，使用两位序号前缀：

```text
01 - 📂 客户材料/
02 - 📝 工作文件/
99 - 待确认/
```

- 序号按分组逻辑排列，不必连续
- 根目录只保留管理文档（材料清单、项目信息、待办事项）
- 分类不确定的材料归入 `99 - 待确认/`

## 不采用的命名方式

- 不要把无法确认的内容写成确定事实
- 不要为了文件名简洁删除展示编号
- 不要用 `重要文件`、`证据1`、`截图2` 这类不可复核名称
- 不要在文件名中加入过长的完整当事人隐私信息；内部使用需保留可识别性时，也应控制长度

## 图片 / 截图命名规则

遇到图片、截图、拍照件时：

1. 先调用当前环境可用的视觉识别或图片理解能力
2. 识别画面类型：聊天截图、付款截图、合同拍照、现场照片、网页截图、证件照片等
3. 提取可见文字中的主体、时间、金额、页面标题、聊天对象等命名要素
4. 给出建议文件名和识别依据

如果图片模糊、截断或无法判断：

- 文件名使用 `待识别` 或 `内容待确认`
- 在材料清单中写明原因
- 不要根据相邻文件强行推断

## PDF 命名规则

处理 PDF 时先分流：

| PDF 类型 | 处理方式 | 命名依据 |
|----------|----------|----------|
| 文本型 PDF | 直接读取标题、首页、目录、落款 | 标题、合同名称、通知名称 |
| 小型扫描 PDF | 可用视觉识别或 OCR 识别首页 / 关键页 | 首页标题、抬头、落款 |
| 大型扫描 PDF | 优先 OCR 或 PDF 文本提取 | OCR 后的标题、目录、关键页 |
| 文件损坏 / 加密 PDF | 标记待人工处理 | 原文件名 + 待解密 / 待修复 |

不要在未读取内容时仅凭 `扫描件.pdf`、`合同.pdf` 直接命名为具体合同。

## 音视频命名规则

遇到音频、视频、录屏：

- 如果文件名无法判断内容，先转写音频或识别关键画面
- 文件名只写内容主题，不展开案件事实
- 录屏要尽量体现画面对象，例如 `平台后台订单记录`、`网页操作留痕`

## 整理执行流程

整理直接在源材料目录上执行（不创建 `organized/` 副本目录）：

1. 建立源目录 `材料清单.md` 和运行时元数据 archive 内的 `materials_manifest.json`
2. 读取目标案件根目录的既有结构、材料清单和编号上限；未指定案件根目录时以源目录现状为准
3. 基于材料说明和 `material_sets` 的集合级理解，规划分组和命名方案
4. 评估参照度，确定 A/B/C/D 分级
5. 经用户确认后执行：重命名文件、创建/重命名文件夹、移动文件到目标文件夹
6. 回更新所有引用：
   - `{文件夹名称} - 材料说明.md` 中的文件路径
   - `材料清单.md` 中的展示路径和文档链接
   - 综合分析中的展示编号引用
   - 运行时元数据 archive 中的 `materials_manifest.json`、`filing_plan.json`、`renaming_map.json`
7. 标记无法确认的材料为 `待人工确认`

每条整理记录保留：

- 原始文件路径
- 原始文件名
- 新文件名
- 后台 `material_id` 与前台 `display_code`
- 所属 `material_set_id` / `material_set_name`
- 参照度判定依据
- 整理时间
- 命名依据和识别方式

## 向后兼容

旧格式 `M-XXX`、`D-XXX` 或 `A-XXX` 可迁移为稳定 `material_id`，原编号写入 `legacy_ids`。新建项目统一使用 `material_id` 作为后台入库身份、`display_code` 作为前台展示编号。
