# 通用 smart-split

在用户希望不同 harness 共用“难题优先强模型、简单任务优先便宜模型”的入口时，维护稳定的 `group/smart-split`。日常只在需要自动分流的模型路径上选择此组；用户有意保留的直连路径继续独立运行。不要求ZCode、Codex等都按同一角色机制配置。

**以下命令在 Skill 目录内执行，`scripts/`、`config/`、`state/` 均相对该目录。**

## 先尊重已有选择

先读取当前用户的画像与实际配置。若用户已确认低成本池允许免费、赠送额度及套餐后备混用，或网关与 CLI 直连并存，则沿用该选择；没有确认时不从组名推断成本边界。只有用户明确要求“绝不扣套餐/积分”时，才需要另立符合该边界的入口。供应商关闭、模型当前不提供等仍是事实，但用户可有意停用一条路线；维护候选与激活生产分开记录。

## 入口与模型组织

让所有已选择此组的 harness 使用同一组ID。协议中的模型是 `group/smart-split`；ZCode等provider目录可能显示为 `magpie/group/smart-split`。使用各客户端实际目录中的ID，不把不同显示拼写当成两个独立策略。

建议外层使用order＋stays=auto，成员为经过任务验收的强模型、套餐执行模型和既有混合池。轻任务规则可以指向嵌套组 `group/free`，后续继续维护池内成员，无需每个harness复制一份规则。池本身的smart/额度安排不代表按智力分流；生成器的smart模板与routing=smart也不是同一个概念。

分类器沿用当前已能稳定工作的低延迟模型，候选免费分类器先测试时延和共享限流；不要仅凭名称便宜就替换。安装版0.1.1265已在临时配置验证支持以组作为分类器，旧网页的单模型限制不作为当前版本事实。首条intent规则可同时传classifier；尚无intent时单独设置分类器会拒绝。

## 规则与默认行为

先核当前规则，按用户确认范围做增量维护，避免重复追加互相遮蔽的模板。可采用下面顺序，模型由当前账户与任务质量选定：

| 顺序 | 条件 | 优先路线 |
|---|---|---|
| 1 | 原生compact请求，且候选已验证可承接上下文与摘要质量 | 当前压缩模型或混合池 |
| 2 | 主规划、架构、复杂根因、关键判断或最终验收 | 强模型 |
| 3 | 边界明确的实现/草稿/指定测试，且处于用户避峰窗口 | 混合资源池优先 |
| 4 | 相同的明确执行任务，其他时段 | 套餐执行模型 |
| 5 | 提取字段、格式化、信息查询等明确轻任务 | 混合资源池优先 |
| 默认 | 分类失败、没有匹配、“继续”等信息不足 | 保守走强模型开头的默认顺序 |

采用2–3种互不重叠的宽泛意图。给子任务开头写清具体工作与验收，帮助分类器理解；不强加固定标签协议。纯“运行命令”不必然简单，涉及部署、删除、敏感判断等仍需要主任务的权限和验收。

不要在意图规则之前放覆盖整个用户时段且无意图限制的强模型 use，避免吞掉晚间的轻任务。不要把客户端默认high/max当成任务困难程度：若在意图前加effort=high，可能令全部子任务走强模型。需要硬性长上下文或图像规则时，用实际能力确定优先路线，不凭“长=难”判断。

时段use只调整优先级，仍可回退；这适合有意混合资源以保持连续执行的策略。只有用户要求某时段绝不消耗某入口时，才用pause，并核嵌套组里同一模型是否仍可到达。不要只暂停外层一个成员就声称所有嵌套/直连路径都被禁止。

## 能力和自动化边界

- 意图路由按新turn决定；同一轮工具调用通常保持模型，以保留缓存与兼容性。子Agent若以独立会话请求同一组，可分别分类。不需要默认把所有主/子Agent改成不同组。
- 子Agent若继承同一组即可利用网关分流；若由客户端固定指定模型或原生直连，则沿用户选择运行，不能承诺这部分也由smart-split控制。`agents=`通常区分客户端，不是通用父/子角色开关。
- use规则是“优先”，不是能力档位硬隔离。允许有意跨档回退，但必须观察实际served model；不能因此承诺最终验收永远由强模型完成。有硬性验收要求的任务可显式选强模型，作为通用组的补充。
- HTTP错误可触发回退；内容错误但请求成功不会触发能力升级。持续推进、任务拆分与验收失败后的升级由harness/既有任务流程处理，网关不替代这些职责。
- 不自动开启已停用供应商、消费卡、改全部客户端默认模型或启动worker。仅维护具名组不代表取得这些动作授权。

## 维护与验证

先固定组前态、配置哈希、成员可用性、CLI版本与允许修改字段。模板覆盖成员、classifier及intent等字段时，当前 `magpie_change.py` 有限schema不能直接承接；走已核原生CLI的逐步计划、私有前态、回读与漂移检查（前态快照存 `state/`），不临时放宽脚本字段校验或整文件重写配置。

把当前个人模型ID、时段和候选命令留在 `config/*.local.json` 与 `state/` 私有层，不进版本库。生产应用与组启用分别核授权；当前停用状态也须保存，不能把“保留/维护一个组”自动解释为激活所有使用者。

先用临时HOME/XDG验证嵌套成员、首条intent设置classifier、规则顺序及CLI真实持久化。实际效果再按经过授权的不同harness请求检查：复杂规划、机械轻任务、明确实现、简短续推、独立子Agent和限流回退。分别观察分类耗时、served model、tool回合、返工和缓存。只做配置回读时标记推理与跨harness联调NOT_VERIFIED。
