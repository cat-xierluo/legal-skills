# Magpie Skill 迭代路线

日期：2026-10-15。状态：已进入实施。私有入库版1.0.0 已实现观测诊断及受控变更/效果比较工具；真实业务收益仍需可比任务验收。

## 定位与目标

将当前“网关路由配置助手”迭代为“个人 AI 工作效能管理”入口。借 Magpie 的观测、额度与配置能力，回答四个问题：资源花在哪里，哪些消耗可能无效，现在怎样安排工作更合适，调整后是否真的提高了单位成果的效率。

核心闭环：观测 → 关联任务 → 诊断 → 提出可验证调整 → 授权范围内执行 → 比较结果 → 保留有效经验。

Magpie 是观测和模型配置的主要接口；任务队列、成果文件与验收结果沿用现有权威来源。Skill 不复制 Magpie UI、不重新实现网关、不另建一套与当前任务源竞争的任务系统。名称统一为 magpie-optimizer，不保留旧名称发现入口。

## 能力边界

| 层 | 主要问题 | 输出 |
|---|---|---|
| 观测 | 钱、套餐和时间花到了哪里 | 按来源、时段、Agent、项目、会话、模型关联的可回查快照 |
| 诊断 | 哪些消耗值得进一步检查 | 带事实、假设、样本范围和建议试验的发现卡 |
| 资源计划 | 现在的额度最适合支持什么工作 | 已有任务与模型/时段/并发的匹配建议 |
| 执行 | 哪些调整可以准确落地 | 网关变更计划、目标前态、回读和恢复路径 |
| 效果复核 | 调整是否降低了交付成本 | 可比任务的质量、返工、时延和消耗对比 |
| 资产沉淀 | 消耗是否留下了可复用成果 | 指向既有产物和验收的轻量关联，不复制原文 |

调整对象不限于模型：也可能是工具返回过长、每轮携带无关 MCP 定义、重复读文件、会话交接、过度派发和消息往返。对应执行仍交给拥有该配置或任务的工具；发现问题不等于获得改写所有 Agent/Skill 的授权。

## 数据与读取契约

1. 优先已安装 Magpie 的 CLI 和有文档的本机 API。桌面内部 API 与网关公开 API 不是同一服务，不把 /api/context 直接套到网关端口。必要时经现有界面读取；本地记录作明确标注的后备数据源。
2. 首次索引允许较长计算：请求异步等待并每约一分钟报告状态，单轮预算可到 180 秒；超时记 pending/incomplete，保留可接续条件，避免多个同类全量扫描并发。未知后台任务不假造 job ID，不盲目无限重试。
3. 响应记录实际观察时刻、时间范围、版本、筛选、分页位置与覆盖量。只读第一页是样本，不能标成完整日账。
4. 区分 through、direct、reported；跨原生会话、网关日志、客户端上报按 Magpie 已知关联去重，没有稳定关联则分列。会话主线程、子任务、辅助标题/压缩调用分开，不直接累加造成重复。
5. 缓存读取、非缓存输入、输出、推理 token 分列；平台估算成本、真实扣费、套餐剩余、积分单位分列。不能把通用 cache 折扣系数当所有平台实付比例。
6. 关联 task_id、session_id、实际服务模型与产物；多个会话可完成同一个任务，一个会话也可能跨任务。关联来源不确定时标未关联，不按标题自动写入权威任务完成状态。
7. 上下文结构用于定位，再按需取具体重样本。不把聊天占比高、exec 多、会话长直接定性为浪费；区分缓存复用、任务难度、工具定义与工具结果。上下文压缩次数若来自启发式推断应明示。
8. 工具名称调用计数不等于 shell 子命令使用计数。细分 rg/git/test 等需解析必要参数；Skill 调用未被显式记录不代表未使用。
9. 默认保留聚合和引用。任务题目、路径、客户材料、命令参数、提示词正文按最小必要使用，私有文件权限 0600，不进公开 Skill 或无关 worker prompt。

## 诊断需要形成可行动的结论

每条发现包含：观察窗口、对象、证据、数据覆盖、解释假设、反证条件、建议动作、效果指标、操作范围与恢复方法。先列少量影响最大且可验证的发现，不用排行榜代替判断。

- 上下文增长快：区分有效进展、冗余输出与累计历史；比较过滤工具输出、索引化读取、阶段交接后的总成本，而非一律新开会话破坏缓存。
- MCP/工具定义占比高：检查任务是否需要这些能力，提出仅对该任务裁剪的配置建议，保留依赖工具。
- 工具往返多：判断是必要探索，还是同一文件重复读取/不必要轮询；优先消除可证的重复。
- 重试和限流多：比较账号总并发、排队、冷却、路由回退及会话粘性，不只增加更多平台。
- 强模型用于易任务：必须用同类任务的验收证据判断可降级，不能用短回复或低 token 推断简单。
- 便宜模型返工多：比较每份验收产物总调用、耗时和人工修订，必要时升级。
- 协作消息多：检查任务拆分、输入完整性和交接频次；不凭 send_message 占比认定多 Agent 无效。

## 资源与成果规划

建议顺序：任务必要性与期限 → 能力和保密要求 → 可用额度/长期窗口 → 到期优先 → 缓存与并发 → 边际成本。额度过期不构成制造任务的理由。

结合用户时段偏好生成“当前可执行／建议稍后／等待输入”的工作建议。例如：临期积分适合有明确产物的索引整理，晚间实际可用的强模型额度留给设计与复核。ZCode 用卡由专用能力负责；本 Skill 不凭预期发卡数自动消费。

成果价值从真实产物及验收取得：来源可回查的索引、可运行脚本、通过验证的测试、用户认可稿件等。目标是提高单位可复用成果的交付效率，不把生成文件数或用完额度视为成功。

## 分阶段退出条件

| 阶段 | 结果 | 退出条件 |
|---|---|---|
| 0.2 观测与诊断 | 完整读取主要维度，解释真实工作中的主要消耗 | 等待/分页/覆盖/来源去重合同可测；用一次真实日样本与 Magpie 界面对账；每条诊断引用证据，未知保留 |
| 0.3 计划与受控调整 | 由诊断生成具体配置或工作流调整，已有对象也可维护 | 演示一次目标明确的变更、回读及恢复；任务质量门槛和跨入口共享额度明确；直接请求不冒称网关可控 |
| 0.4 效果与个人经验 | 找到对本人真实有效的模型和工作方式 | 至少跨多个代表性任务比较质量、返工、耗时与消耗；记录任务难度与供应商变化等混杂，不把历史回放当真实质量试验 |
| 后续：按授权持续管理 | 按需检查异常、到期资源和已批准任务机会 | 有实际长期授权、安静通知规则、人工覆盖优先和停止条件；不默认创建定时器或无人值守派发 |

验收分别覆盖 API 汇总对账、GUI 同日逐项核对、已有组修改与恢复，以及真实任务的效果比较；缺少哪类证据就将该项记为 NOT_VERIFIED。角色分层是待验证的初始假设，不在缺少任务证据时扩展为固定全局最佳配置。已有 Magpie“为你调优”结果可作为候选输入，但要核它覆盖的成本模型、样本和可控对象，不能由 token 回放替代任务质量验证。

## 主要风险与重新评估条件

- 大规模会话索引耗时：限制并发、分页与增量，不能以短超时反复全量重扫。
- 版本改变接口：能力探测与字段契约隔离；脚本与文档核对安装版，不只跟随 upstream main。
- 不同任务难度、学习效应和平台变化污染对比：使用同类任务及明确质量底线，结论保留证据范围。
- 跨平台副作用：账号卡、任务派发、MCP/Skill 修改保留各自工具边界；协调不扩大写入范围。
- 诊断本身耗费过大：统计优先本地确定性聚合，模型只看必要摘要，按需深入具体会话。

## 版本与证据

- 早期接口核验基于 CLI 0.1.1237；当前使用前重核安装版，具体读数与证据保存于私有 state。
- 路由历史与会话缓存只证明实际读取的样本范围，不能据此宣称覆盖全量。
- [Magpie Context 实现](https://github.com/yetone/magpie/blob/main/internal/gui/context.go) 供理解字段与估算边界；实时安装行为优先。
