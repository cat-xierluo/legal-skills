# Multi-Agent Peer Session

MAO（multi-agent-orchestration）负责**本项目内的 worker 派发与返回**；本 Skill 负责**跨 runtime 对等会话的直接通信**——发现对方的持久会话、唤醒一个回合、投递结构化消息、同步等待结论、回流消化。两者构成一套：MAO 派发→执行→本 Skill 审计→回流→下一轮派发。

当前验证的通道：**ZCode 会话 → Codex 会话**（上游 PM / 总控入口）。反向（Codex → ZCode）无对等机制，见 §6。

## 1. 适用边界

使用本 Skill：

- 批量交付收口后，需要**上游/更强模型**交叉审计自评是否过宽。
- 双端独立判断有价值的场景：上游实跑核验、模板/schema 归因、行为取舍评估。
- 需要向对方会话通报进度并**避免重复开工**的对齐消息。
- 用户说"发上游审计""让 Codex 审一下""交叉审计"。

不要使用：

- 同 runtime 的 worker 派发/返修/验收（用 MAO）。
- 一次性文件读取或 git PR 内的常规代码审查（独立评审 subagent 即可）。
- 消息内容含密码、密钥或客户敏感材料（会写入对方会话的持久历史）。

## 2. 会话发现

对方会话是**持久对话记录**，不是常驻进程。要找到它：

### 2.1 从任务源定位会话 ID

```bash
# 在项目任务文档中 grep 会话 UUID（8-4-4-4-12 格式）
grep -rn "01a0f[0-9a-f-]*" docs/TASKS.md AGENTS.md --include="*.md" | sort -u

# 或搜"总控"/"PM"/"上游"等角色标注附近的 UUID
grep -rn -B1 -A1 "总控\|PM" docs/TASKS.md | grep -oE "[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}" | sort -u
```

### 2.2 从 Codex 会话存储验证

```bash
# Codex 会话文件在 ~/.codex/sessions/YYYY/MM/DD/rollout-*-<uuid>.jsonl
# 按日期目录 + UUID 前缀定位
find ~/.codex/sessions -name "*<uuid前8位>*" -type f

# 验证是正确的会话：看首条 session_meta 的 cwd 和初始指令
head -1 <文件路径> | python3 -c "
import json,sys
d=json.loads(sys.stdin.read())
p=d.get('payload',{})
print('session_id:',p.get('session_id'))
print('cwd:',p.get('cwd'))
print('timestamp:',p.get('timestamp'))"
```

### 2.3 多个候选时的判定

- 按 `session_meta` 的 `cwd` 判断归属项目。
- 按文件修改时间判断活跃度（但注意：session 文件 mtime 可能被统一 touch，以最后事件的时间戳为准，见"PM 会话活性判别法"）。
- 按任务源中的具名标注判定（如"Legal Skills 总控入口 插件 PM"）。

## 3. 唤醒与消息投递

### 3.1 同步模式（主路径，已实跑验证）

```bash
CX="<codex-cli 二进制绝对路径>"  # 见 §3.3
"$CX" exec resume <对方会话UUID> - <<'MSG'
【<你的角色>→<对方角色>｜<请求类型>；只读核验/不改派任务/不需回执之外的动作】

<结构化消息正文——见 §4 的消息契约>
MSG
```

**同步阻塞**：发出后等待对方处理完毕（本轮实测约 7 分钟 / ~1690 万 token），stdout 输出最终结论，进程退出后你直接读到结果。

### 3.2 排队模式（不唤醒，对方下次打开时才看到）

```bash
"$CX" queue --thread <对方会话UUID> --message "<消息文本>"
```

适用于：不需要立即结论、对方正在处理别的事、或你自己即将离场。

### 3.3 CLI 二进制定位

codex CLI 可能不是 `which codex` 找到的那个。可靠的定位方式：

```bash
# 方式1：标准安装
which codex

# 方式2：ChatGPT.app 内嵌（macOS）
ls "/Applications/ChatGPT.app/Contents/Resources/codex-cli/bin/codex"

# 方式3：验证版本
<CX路径> --version
```

## 4. 消息契约（审计请求的标准格式）

```
【<来源角色>→<目标角色>｜交叉审计请求；只读核验请求，不要求代派，不需要回执之外的任何动作】

我（<你的身份>）<一句话背景>。<台账/证据入口>，请你们作为<上游/更强侧>一起做交叉审计，重点核我们有没有自评过宽的地方：

一、合入清单（全部经独立评审 + 本地 CI）：
- <PR 编号>：<一句话描述>（<关键验收事实>）
- ...

二、请重点交叉审计的 N 处（我们自评可能过宽）：
1. <具体方法/行为>：我们做了 X——请独立判断 <具体疑点>。
2. ...

三、待办同步：<我方剩余项及外部依赖>。若上游侧对上述任何一项有计划，请在你们的任务源登记并对齐，避免两边重复开工。

证据入口：<具体路径>。挂起事项：<如有>。此消息仅请求核验与对齐，不改派任何在途任务。
```

关键原则：
- **只读核验**：明确告知对方不要求代派、不改写任务源、不认领修复。
- **自疑点前置**：把你自己最不确定的地方列出来（这比泛泛"请审一下"有效得多）。
- **证据指针**：给出具体 TASKS/PR/evidence 路径，对方有工具可以自行实跑。
- **角色标注**：双方身份明确，避免对方误以为你是它管理的 worker。

## 5. 结论回流与消化

对方回复后（stdout 或从 rollout 文件读取），按以下步骤消化：

1. **逐条验证**：对方给出的每个发现（P1/P2/P3），回到代码/测试独立验证是否属实——不盲信也不盲拒。
2. **修复或登记**：
   - 属实且可修→修复 + 反例回归→ PR → 合入。
   - 属实但非当前优先级→在所属插件 TASKS 登记后续卡。
   - 不属实→礼貌记录但不合入（保留对方意见原文，写明你方判断依据）。
3. **台账回写**：把交叉审计结论 + 消化结果记入 docs/TASKS.md（一条，含 PR 链接与证据指针）。
4. **归因修正**：如果对方指出你方自评过宽/归因错误，修正原卡的措辞。

## 6. 双向限制与治理

| 方向 | 通道 | 状态 |
|---|---|---|
| ZCode → Codex | `codex exec resume` / `codex queue` | **已验证可用** |
| Codex → ZCode | 无直接对等机制 | 需通过文件共享（TASKS/git）或用户转达 |

### Token 消耗报备

- 对方审计回合消耗的是**对方账户的 token**（本轮实测约 1690 万）。
- 预估消耗超过 **500 万 token**（如涉及大量实跑/工具调用）时，先向用户报备再发送。
- 小额审计请求（纯读文档/轻量核验）可自主发送，事后在台账记录消耗量。

### 并行会话安全

- 唤醒前确认对方会话当前不活跃（最后事件时间戳 > 30 分钟前），避免与其在途回合冲突。
- 不要在对方正在活跃工作的会话上投递大量消息。
- 唤醒回合的内容会持久写入对方会话历史——后续任何一方 resume 都会看到，这是特性不是 bug。

## 7. 会话命名约定（推荐）

为便于发现和维护，建议双方会话名遵循配对命名：

```
<项目名>｜<角色>（<方向>）
```

示例：
- Codex 侧：`dsh-plugins｜上游总控（上游）`
- ZCode 侧：`dsh-plugins｜PM 接手（下游）`

**重命名方法**：Codex Desktop App 的 app-server 协议含 `thread/name/set` 方法（参数 `{threadId, name}`），但需要 daemon 正常运行且 Desktop App 不冲突时才可用。实际操作中更可靠的方式是：
- 在 Codex Desktop App 里手动重命名线程（UI 操作）。
- 或在首次唤醒时，消息正文首行注明"请将本会话重命名为 `<约定名>`"——对方回合有工具能力时可以自行处理。

## 8. 已验证实例

2026-10-04，dsh-plugins 项目 PM（ZCode 会话）→ Legal Skills 总控（Codex 会话 `01a0f152-3402-…`）：

- **通道**：`codex exec resume` + 结构化审计请求（合入 22 个 PR 的清单 + 3 处自疑点）。
- **对方行为**：只读核验 7 分钟、~1690 万 token、11 次命令执行 + 9 次推理 + 3 条结论。
- **产出**：证实合入事实全部正确；纠正 3 处自评过宽（1 个新引入 P2 + 1 个既有 P2 + 1 个 P3）；另发现并行会话完成的 #122 有 P2 运行投影串扰。
- **回流**：#135 修复合入（3 个反例回归）；F1 串扰卡登记；归因修正写入 elements TASKS。
- **消耗**：1690 万 token（对方账户），事后向用户报备并获认可。
