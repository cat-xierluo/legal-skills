# Upstream Sync（上游功能变更同步）

把「下游项目感知上游仓功能演进」固化为可定时运行的循环。首战：dsh-plugins ← hermes-plugins（2026-09-30，PR #50——真实生产跑 Hermes 插件、DSH 侧并行重写，用户在上游修 bug/调功能，下游要对齐**功能意图**而非代码）。

**核心原则**：两边实现必然不同（平台/架构差异），同步的是**功能语义与修正意图**——永不做代码搬运。

## 1. 适用前提（缺一不进入）

| # | 前提 | 说明 |
|---|---|---|
| 1 | **血统上游仓** | 下游项目业务源自该仓（用户真实生产在跑），且本机可读（通常同机 git 仓） |
| 2 | **映射关系** | 上游模块 ↔ 下游插件的对应表（放项目 config，脚本消费） |
| 3 | **基线水位** | 一个 git SHA（血统分叉/迁移时点），漂移 = 水位以来的 diff + 在途未提交 |
| 4 | **登记表** | 项目内文档（如 docs/UPSTREAM-SYNC.md）：条目 = 来源/功能意图/消化决定 |
| 5 | **消化出口** | 下游项目的任务源（两层治理时是各插件 TASKS）——同步最终要落成 task，不是读完就完 |

## 2. 检测层（脚本，属项目仓库）

每项目一份漂移探测脚本（首例：dsh-plugins `scripts/check-upstream-drift.mjs` + `config/upstream-sync.json`）。要点：

- **报告模式**：对照基线水位报告已提交 + 在途（未提交）漂移，永远退 0——漂移是信息不是失败。
- **水位推进**：`--update-baseline` 只在漂移「已登记消化」后执行（防重复报告）；在途变更单独标注（用户正在改，不抢跑）。
- 上游有多个下游关注模块时，映射表驱动扫描范围；已有独立同步流程的模块（如 subtree）排除。

## 3. 巡检循环（理解层，本 skill 的核心——LLM 工作）

**手动模式**：开发对应模块的切片前必跑一次检测并查登记表（写入下游 AGENTS 规则）。
**定时模式**：cron 驱动（参考 night-autopilot 的巡检模式），每轮：

1. **检测**：跑脚本。
2. **理解**（需智能，非脚本能做）：对**新提交**的漂移读上游 diff + commit message，提取功能意图——修了什么问题、行为怎么变、影响下游哪个已实现/将实现的层；拿不准处**问用户**（定时模式下标注待确认，不猜）。**在途（未提交）漂移只标注不解读**（用户正在改，语义未定）。
3. **登记**：登记表开条目（SYNC-xxx）：来源（SHA/未提交）、功能意图、影响面。
4. **同步进 task**：在下游任务源开同步卡或待办项——两层治理时写进对应插件 TASKS（标注「上游同步：xxx」），判定二选一：**平移**（下游实现对应行为，进切片计划）或**不适用**（写明理由：平台原生已覆盖/语义已不同实现/仅上游特有）。
5. **推进水位**：该批全部登记消化后 `--update-baseline`。

## 4. 纪律

- 只同步功能意图；代码、平台特有 hack、上游试验性代码不平移。
- 在途变更等提交（语义未稳定）；用户口述意图优先于 diff 推断，冲突时确认。
- 「不适用」必须写理由——这是将来复盘「为什么两边行为不同」的唯一线索。
- 定时巡检的每轮动作有界：检测 + 理解新漂移 + 登记；平移实现走正常开发流程（worker/切片），不在巡检里顺手改代码。

## 5. 与其他 skill 的关系

- 定时驱动与巡检纪律参考 [night-autopilot](../night-autopilot/SKILL.md)（可并入其巡检项，也可独立 cron）。
- 检测脚本属项目仓库（非 skill 自带）——skill 是流程与判断层，脚本随项目走。
- 下游开发规范（如插件开发）仍归各自 dev skill；本 skill 只管「上游变化进来」这一段。

## 6. 已知限制

- 理解层依赖 LLM 读 diff，大变更（数千行）需分模块提取；拿不准必须问用户，宁可漏不可错。
- 在途漂移只可见「文件清单」，功能意图要等提交或用户口述。
- 单机前提（上游仓本机可读）；跨机上游未覆盖。
